The DAW as Bottleneck

A producer working in REAPER who decides that the vocals need to be warmer faces a translation problem. The intent is musical and holistic; the realization is a sequence of low-level moves across EQ, saturation, compression, and possibly a send to a tape emulation. The Digital Audio Workstation, in the form that has been stable since the early 2000s (Leider, 2004), affords fine control over each of these moves but offers no first-class representation of the intent that motivates them. Kjus (2024) characterizes this as a platformization effect, in which the tool maximizes the surface area of possible operations and leaves coordination of those operations to the practitioner. Modern AI-driven music generators sit at the opposite extreme. Systems such as Suno (2024) produce finished tracks from a sentence, but do so as one-shot artifacts that exit the iterative loop in which most music is actually made.

This session examines two recent papers that probe the space between these extremes. We pair them because they ask the same question from opposite sides. Elkins et al. (2025) describe a system, DAWZY, that maps natural language requests onto reversible script actions inside a real DAW. Son et al. (2026) describe the underlying interaction problem the field will eventually face once such systems are common, by characterizing the patterns through which professional creatives actually want to work alongside a continuously executing agent. The first paper shows what is possible today; the second shows the shape of what is not yet supported.

The single-turn ceiling
DAWZY treats every request as a request-response: speak, listen, execute, undo if wrong. Son et al. find that across 214 logged turns of professional designers working with a process-visible agent, only 70% follow that pattern. The remaining 31.8% involve concurrent action, in which the user is editing the same artifact the agent is editing, at the same time. Most agent architectures, DAWZY included, cannot see those turns at all.

Reversible Action

DAWZY's design refuses the brittle pattern in which an LLM rewrites the project file directly. Each request is compiled into a Lua ReaScript that ReaPy executes against live session state, and every script is constructed so its effect can be reversed with a single undo. We posit that this is the load-bearing safety primitive of the system. A probabilistic generator, sitting in front of a deterministic editor, can only be trusted if the editor preserves a path back to the previous state.

MCP as Interop Layer

DAWZY exposes three Model Context Protocol tools to the LLM, namely a state query that enumerates tracks, items, FX, and routing; an FX parameter setter that translates human units (dB, ms) into ReaScript slider ranges; and a local invocation of MusicGen-small for generated audio. The salient design move is that unit translation is handled by a tool rather than by the model. The authors report that GPT-5 reliably failed at converting between dB and the 0-to-1 slider range that REAPER's plugin API expects, and so they removed the responsibility from the LLM entirely.

Concurrent Action

The central finding of Son et al. is empirical rather than conceptual. Across 214 turns of professional designers working with their second probe system, concurrent action (the user editing the artifact while the agent edits the same artifact) appeared in 31.8% of turns. Five distinct concurrent patterns are reported, including in-situ co-editing, artifact takeover, and demonstration-based steering. We note that no current music-AI agent system, DAWZY included, has an architectural slot for this category of behavior, because no current music-AI agent system can perceive simultaneous user modifications to the artifact it is editing.

Six Triggers

Son et al. identify six conditions that prompt users to shift from observing the agent toward intervening with it. The triggers include misaligned task interpretation, idea spark from agent's work-in-progress, readiness for fine-grained detailing, and execution quality drop. The first three lead users into concurrent action; the last triggers verbal redirection or termination. The decision model that links triggers to action categories, mediated by four enabling factors (mental model of agent capability, perceived task importance, preferred intervention modality, expected agent response), is the paper's central contribution.

DAWZY: Natural Language as Control Surface

Elkins et al. (2025) introduce DAWZY as a three-layer pipeline (User Interaction, Processing, Execution) mediated by an Electron desktop application that wraps REAPER. The User Interaction layer accepts text, speech (transcribed by Whisper), and humming (converted to MIDI by Spotify’s BasicPitch model). The Processing layer routes the resulting query to an LLM, which is responsible for interpreting intent, selecting MCP tools, and emitting Lua ReaScript. The Execution layer runs the generated script against the live REAPER project via ReaPy, with all changes constructed to be reversible.

The hum path takes a different branch in the Processing layer (BasicPitch instead of fx_param), but the Execution layer still produces a reversible script. We note that the design decision to route every modality through the same Lua-emitting pipeline, rather than building modality-specific execution paths, is what keeps the undo affordance uniform across the system.

The architectural choice that bears closer examination is the separation between code generation and structured tool calls. The LLM emits Lua for the project-shape edits that benefit from compositional flexibility (e.g., “duplicate the first track, pitch it up one octave, and blend it in at 20%”), but delegates parameter-setting to a dedicated tool that maintains a unit-conversion table. The authors report that open-source baselines (Qwen3-Coder-480B, GPT-OSS-120B, GPT-OSS-20B) achieved only 25 to 50% success on their four reproducible tasks, frequently producing hallucinated ReaScript functions or mis-indexed parameters. GPT-5, evaluated on the same tasks, was the only model that generated reliable edits across all four. We posit that the gap reflects training data rather than architecture, since REAPER’s ReaScript API is one of the older and more publicly documented DAW scripting layers, and Ableton-MCP (Anthropic, 2024), evaluated on Ableton Live’s newer and less documented API, failed to complete two of three qualitative tasks even when paired with Claude Sonnet 4.5.

The subjective evaluation is small but instructive. A Mean Opinion Score test with N=21 participants rated DAWZY across five criteria. Enjoyment received the highest score (4.48 / 5), followed by Learning (4.38), Collaboration (4.29), and Usability (4.14). Control received the lowest score (3.81), with a notably wider interquartile range than the other four dimensions. We observe that this echoes the surprisal-control paradox reported in ReaLJam (Scarlatos et al., 2025) and discussed in our prior session, in which musicians who felt more in control of an AI accompanist rated their sessions lower. The two systems differ in domain (real-time accompaniment versus DAW production) and in evaluation cohort, but the directionality of the effect is consistent. Whether this reflects a genuine preference for AI surprise or a measurement artifact of small samples we leave open.

CLEO: When Delegation Is Not Enough

Son et al. (2026) approach the same general problem from the side of the human user rather than the system. Their domain is web design in Figma rather than music production in REAPER, but we read the paper as a study of co-creative agents in general, on the grounds that the underlying interaction patterns concern artifact manipulation under shared cursors, which transposes naturally to a multitrack project.

The paper reports two studies. The first study (N=10 professional designers) used an initial probe agent built on the ReAct architecture (Yao et al., 2023), in which the agent’s tool calls were rendered visible on the canvas as they executed. The finding that motivated the second study is that process transparency, on its own, was insufficient. Designers reported a strong desire to intervene mid-execution (i.e., to edit elements the agent was working on, or to take over partial outputs and refine them in parallel), but the system could not distinguish such interventions from independent user work. The conflict reported by participants is precise: the agent’s plan would attempt to undo or revert the user’s concurrent edits, because the plan had no representation of the user as a co-actor on the shared artifact.

The second probe, CLEO (Collaborative Linked Executive Operator), extends the ReAct loop with three modules positioned to address this gap. A User Change Detection Module analyzes the diff between the prior agent response and the current canvas state to capture modifications made while the agent was inactive. An Attribution Change Module distinguishes agent-attributable changes from user-attributable changes at each iteration boundary. A Plan Update Module revises the plan only when user modifications conflict with the existing plan or indicate new directions. The two-day study (N=10) that followed produced 214 turn-level segments of human-agent interaction, with each segment annotated against five action categories.

The five categories (and their distribution across the 214 turns) are:

We note that the shares sum to more than 100% because turns frequently include multiple action categories in sequence. Hands-off and Observational behaviors co-occur in 14% of all turns (users monitoring agent work they have delegated). The Concurrent category itself decomposes into five distinct patterns, of which demonstration-based steering (showing the agent a desired change through direct editing rather than verbal instruction) and in-situ co-editing (user and agent working simultaneously on the same subtask and artifact) are the patterns least supported by current agent architectures.

Five Action Patterns · CLEO

Toggle the five patterns. The percentages sum to more than 100 because Son et al.'s coding allows up to five categories per turn. The pattern most current music-AI agents cannot perceive is Concurrent: the overlap region marks edits both the user and the agent are making to the same artifact at the same time.

Cycle through the five patterns to feel the asymmetry. The first four (Hands-off, Observational, Directive, Terminating) are all variations on turn-taking, and any architecture that can route a request and emit an output can support them. Concurrent is structurally different: the agent's plan and the user's edits intersect on the same artifact, and the system has to attribute changes correctly to avoid undoing the user's work. The CLEO add-on modules (user-change detection, attribution, plan update) exist exactly to handle this 31.8% slice.

We posit that these two patterns are the locus of the gap the paper identifies. They require the agent to perceive user actions and to interpret those actions as positive or negative behavioral signals about how the user wants the work done.

The paper’s decision model captures the routing logic empirically. Given a trigger (an observable condition that prompts the user to consider intervention) and an enabling factor (the user’s preferred intervention modality, beliefs about agent capability, and current task priorities), the model predicts which of the five action categories the user is most likely to select. We find the model most useful as a tool for active reading: tracing concrete combinations through it reveals which trigger-modality pairs the data supports and which it does not.

The blocked paths (dashed red) are as informative as the open ones. A user observing an idea spark from the agent's work-in-progress never proceeds to verbal redirection in the data, because the trigger by construction is a generative one: the user wants to build on what the agent produced, not to correct it. The same combinatorial constraint holds for need for early outcome visibility. We read these constraints as design hints rather than empirical curiosities, in that the agent should respond to triggers with anticipated action categories rather than treating every intervention as undifferentiated feedback.

How They Compare

The two papers are best read as occupying adjacent positions on a continuum that runs from delegation-as-fire-and-forget to fluid concurrent co-creation.

DimensionDAWZY (Elkins et al., 2025)CLEO (Son et al., 2026)
DomainMusic production (REAPER)Web design (Figma)
ContributionSystem and open-source prototypeDecision model and annotated dataset
Interaction patternRequest-response, single turnContinuous execution with intervention loops
Agent backboneGPT-5 + 3 MCP toolsClaude Sonnet 4.5 + 38 Figma tools
What the agent seesLive DAW state on each tool callLive canvas state + diff of user changes
Concurrent user actionNot represented architecturallyDetected, attributed, integrated into plan
Evaluation4 objective tasks + MOS (N=21)2 design probes, 214 turns coded (N=10+10)
ReversibilityAtomic ReaScript + undoReAct iteration boundaries (10-cycle cap)

The pairing makes a forward-looking claim more than a comparative one. DAWZY shows that, in mid-2025, a small academic team can stand up a functioning natural-language-to-DAW agent that survives the user studies it is given. Son et al. show, in the same year, that the agents which will eventually replace it cannot be evaluated solely on the success rate of their atomic edits. Roughly a third of meaningful collaboration is concurrent rather than turn-taking, and that fraction is invisible to any architecture that treats the user as a request generator. We note that closing this gap will likely require changes at three levels of the music-AI agent stack: tool definitions that support partial-result inspection, plan representations that admit user-attributable edits, and interface affordances (the spatial signals Son et al. propose, in which agent cursor position, viewport focus, and edit proximity all communicate collaborative intent) that have no current analog in any DAW we are aware of.
